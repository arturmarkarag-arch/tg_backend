# Аудит перенесення продавця між магазинами та групами

Дата: 2026-08-06  
Версія: `client(10)` + `server(11)` до наступних виправлень  
Статус: аудит без зміни бізнес-логіки перенесення

## Область перевірки

Перевірено всі знайдені шляхи, які можуть змінити `User.shopId`:

1. адмінська зміна користувача: `PATCH /api/users/:telegramId/shop`;
2. загальне редагування користувача: `PATCH /api/users/:telegramId`;
3. масове призначення в картці магазину: `PATCH /api/shops/:id/sellers`;
4. заявка продавця та її схвалення: `POST /api/shop-transfer/:id/approve`;
5. пряма зміна власного магазину: `PATCH /api/v1/telegram/me/shop`;
6. використання одноразового запрошення магазину: `redeemShopInvite()`;
7. створення/повторний `POST /api/users`;
8. зняття продавця з магазину: `unassignSellerAndPark()`.

Перевірено пов'язані сутності:

- `User.shopId`;
- `User.deliveryGroupId`;
- `User.warehouseZone`;
- `Shop.deliveryGroupId`;
- `DeliveryGroup.members`;
- активний `Order` та `buyerSnapshot`;
- `PickingTask`;
- локальний `cartState`;
- socket-події й кеш магазинів;
- журнали `User.history`, `Order.history`, `ShopAuditLog`.

## Бажане джерело правди

У коді вже задекларована правильна модель:

```text
User.shopId → Shop.deliveryGroupId → DeliveryGroup
```

`User.deliveryGroupId` і `User.warehouseZone` зараз є денормалізованими копіями для швидкого читання. Вони мають завжди виводитися з поточного магазину, а не редагуватися самостійно.

> **Статус на 07.08.2026: закрито.** Обидва поля прибрані зі схеми `User` і з бази
> (`scripts/normalizeUserGroup.js`), каскад у `routes/shops.js` видалено. Далі в цьому
> документі вони згадуються як опис стану на момент аудиту. Див. `docs/architecture/technical-debt.md`.

`DeliveryGroup.members` вважалося видаленим джерелом правди, але поле досі є в Mongoose-схемі `DeliveryGroup`. Продакшн-логіка майже не читає його, однак наявність поля створює ризик повторного використання застарілого масиву.

# Підтверджені проблеми

## P0 — продавець може обійти схвалення перенесення

Endpoint:

```text
PATCH /api/v1/telegram/me/shop
```

захищений загальною авторизацією, але не має обмеження ролі. Клієнтський UI для продавця правильно створює `ShopTransferRequest`, однак продавець із чинною сесією може напряму викликати цей endpoint і одразу змінити магазин через `migrateSellerShop()`.

Так само endpoint технічно доступний працівнику складу, хоча UI не показує йому зміну магазину.

### Наслідок

- обхід адмінського погодження;
- можливе призначення до зайнятого магазину;
- можливе створення конфлікту продавців і замовлень.

### Рекомендація

Дозволити пряму `/me/shop` лише ролі `admin`. Продавець повинен використовувати виключно `/shop-transfer`, працівник складу не повинен мати можливості отримати `shopId`.

---

## P0 — початкове призначення після зняття залишає припарковане замовлення

Під час зняття продавця `unassignSellerAndPark()` відв'язує його незбиране активне замовлення від магазину:

```text
Order.shopId = null
buyerSnapshot.shopId = null
buyerSnapshot.deliveryGroupId = ''
```

Після цього продавець без магазину може створити заявку на нове призначення. У `shopTransfer` цей випадок визначається як `isAssignment`, але при схваленні код просто оновлює `User.shopId` і не викликає `migrateSellerShop()`.

### Наслідок

Продавець уже сидить у новому магазині, а його активне замовлення залишається припаркованим без магазину й групи.

### Рекомендація

Початкове призначення наявного користувача також проводити через `migrateSellerShop()`. Цей сервіс уже має окрему гілку, яка знаходить припарковане активне замовлення продавця.

---

## P1 — різні шляхи мають різну політику зайнятого магазину

`shop-transfer/:id/approve` перевіряє конфлікт і вміє витіснити одного поточного продавця.

Інші шляхи не мають такої самої перевірки:

- `PATCH /users/:telegramId/shop`;
- `PATCH /users/:telegramId`;
- `PATCH /shops/:id/sellers`;
- `redeemShopInvite()`;
- `PATCH /v1/telegram/me/shop`.

### Наслідок

До одного магазину можна призначити кількох продавців, хоча інша частина системи вже трактує `2+` продавців як конфлікт.

### Потрібне бізнес-рішення

Перед виправленням треба обрати єдине правило:

1. **Блокувати**, якщо магазин уже має продавця;
2. **Витісняти** поточного продавця з паркуванням його замовлення;
3. дозволяти кількох продавців свідомо, але тоді прибрати трактування цього стану як конфлікту.

Нинішня поведінка змішана й залежить від того, якою кнопкою виконано перенесення.

---

## P1 — масове призначення не бере персональні блокування продавців

`PATCH /shops/:id/sellers` запускає Mongo-транзакцію, але не використовує блокування:

```text
user:<telegramId>:shop
```

Такі блокування вже використовують:

- пряме адмінське перенесення;
- схвалення заявки;
- запрошення магазину;
- самостійна зміна магазину.

### Наслідок

Масове призначення може одночасно виконуватися із:

- другим адмінським перенесенням;
- використанням invite-посилання;
- схваленням заявки;
- зміною або створенням активного замовлення.

Транзакція захищає власні записи, але не серіалізує два різні бізнесові сценарії на одному продавці.

### Рекомендація

Брати стабільно відсортовані `user:<id>:shop` locks для всіх `toRemove` і `toAdd` перед транзакцією.

---

## P1 — витіснення продавця дублює й обходить основний сервіс зняття

У `shopTransfer` витіснений продавець обробляється ручними `User.updateOne()` та `Order.updateOne()` замість `unassignSellerAndPark()`.

Через це для витісненого продавця не гарантуються однаково:

- `Shop.lastSeller`;
- `lastSellerChangedAt`;
- повний `ShopAuditLog`;
- `User.history`;
- однакова логіка для всіх його активних замовлень;
- єдина точка майбутніх виправлень.

### Рекомендація

Замінити ручну гілку на `unassignSellerAndPark()` і доповнити сервіс поверненням списків parked/in-pipeline замовлень для UI та socket-подій.

---

## P1 — прямі адмінські перенесення не повідомляють відкритий Mini App продавця

`shopTransfer` після commit надсилає:

```text
user_shop_changed
```

Але прямі шляхи через `/users/:telegramId/shop`, `/users/:telegramId` і `/shops/:id/sellers` цієї події не надсилають системно.

Клієнт уже має listener, який після `user_shop_changed` перечитує профіль і чистить shop-scoped React Query cache.

### Наслідок

Якщо продавець тримає Mini App відкритим під час адмінського перенесення, інтерфейс може продовжувати показувати старий магазин і стару групу до перезапуску або випадкового refetch.

### Рекомендація

Зробити єдиний post-commit notifier для всіх шляхів:

- `user_shop_changed` для кожного переміщеного/витісненого продавця;
- `user_order_updated`, якщо замовлення переміщено або припарковано;
- `shop_status_changed` для старої й нової групи;
- `delivery_groups_updated`, якщо змінився груповий контекст.

---

## P1 — адмін може призначити продавця до неактивного магазину

`shop-transfer` та invite перевіряють `Shop.isActive`.

Прямі адмінські маршрути знаходять магазин лише за `_id`, а `migrateSellerShop()` сам не перевіряє `isActive`:

- `/users/:telegramId/shop`;
- `/users/:telegramId`;
- `/shops/:id/sellers`.

### Наслідок

Продавець може отримати неактивний магазин і формально правильний `deliveryGroupId`, але нормальний користувацький сценарій такого призначення не допускає.

### Рекомендація

Перевірку `isActive` винести в централізовану команду призначення. За потреби додати окремий явний `allowInactive` тільки для спеціального адмінського відновлення.

---

## P2 — `POST /api/users` може сиро оновити наявного користувача

Якщо `telegramId` уже існує, `POST /users` виконує звичайний `findByIdAndUpdate()` із санітизованим payload.

Якщо в такому запиті змінити магазин, `User.shopId` і денормалізована група зміняться, але активне замовлення, picking і журнали не пройдуть через `migrateSellerShop()`.

Клієнт використовує `POST` лише для створення, але серверний маршрут фактично є прихованим upsert/update-шляхом.

### Рекомендація

При наявному `telegramId` повертати `409 user_exists`, а зміни дозволяти лише через `PATCH`.

---

## P2 — з кількох припаркованих активних замовлень повертається лише одне

`unassignSellerAndPark()` може припаркувати всі активні замовлення продавця на магазині.

Під час призначення продавця без магазину `migrateSellerShop()` шукає лише один документ:

```text
findOne(...).sort(updatedAt, createdAt)
```

### Наслідок

За наявності кількох legacy/stale активних замовлень лише найновіше перейде до нового магазину, решта залишаться припаркованими.

### Рекомендація

Або гарантувати й перевіряти invariant «не більше одного parked active order на продавця», або при перенесенні явно повертати конфлікт зі списком замовлень для ручного рішення.

---

## P2 — навігація каталогу скидається не однаково

Різні шляхи передають різний `resetCartNavigation`:

- схвалення transfer request: `true`;
- `/me/shop`: `true`;
- прямий адмінський assign: за замовчуванням `false`;
- bulk assign: `false`;
- invite redeem: за замовчуванням `false`.

### Наслідок

Після перенесення продавець залежно від способу може:

- почати з першого товару;
- залишитися на позиції старого магазину/сесії.

### Рекомендація

Визначити одне правило. Найбезпечніше: при зміні `shopId` скидати лише навігацію каталогу, але не очищати `cartState.orderItems`.

---

## P2 — модель `DeliveryGroup.members` суперечить поточній архітектурі

`utils/deliveryGroupMembers.js` і міграційний скрипт стверджують, що `DeliveryGroup.members` більше не є частиною моделі й має бути видалене з БД.

Фактично поле досі оголошене в `models/DeliveryGroup.js`.

Продакшн broadcast закоментований, тому сьогодні це не ламає перенесення. Проте майбутній код може випадково знову почати читати stale `members`.

### Рекомендація

1. видалити `members` із Mongoose-схеми;
2. виконати `scripts/dropDeliveryGroupMembers.js --execute` після dry-run;
3. не зберігати склад групи окремо — обчислювати через `Shop.deliveryGroupId` та `User.shopId`.

# Що вже зроблено добре

- основна міграція виконується в Mongo-транзакції;
- є per-seller lock у більшості одиночних шляхів;
- активне замовлення не дозволяється рухати після входу в picking pipeline;
- перенесення в групу, де picking уже стартував, може відправити замовлення в наступну сесію;
- старі історичні замовлення не переписуються заднім числом;
- припарковане замовлення очищає стару групу, тому не потрапляє в picking як «невідомий магазин»;
- кеші старого й нового магазину інвалідовуються після commit у центральному сервісі;
- є durable `ShopAuditLog` для основного шляху міграції.

# Запропонована цільова конструкція

Усі шляхи повинні викликати одну команду, наприклад:

```text
assignSellerToShop({
  sellerTelegramId,
  targetShopId,
  actor,
  occupiedShopPolicy: 'reject' | 'displace',
  resetNavigation: true,
  source,
})
```

Команда повинна централізовано:

1. взяти locks усіх заторкнутих продавців;
2. перевірити активність і конфлікт магазину;
3. зняти/припаркувати витісненого продавця через один сервіс;
4. перенести або припаркувати активне замовлення;
5. оновити `User.shopId` і похідні поля;
6. записати всі журнали;
7. повернути post-commit actions для cache/socket;
8. не дозволити жодному маршруту робити сирий `$set: { shopId }`.

# Рекомендований порядок виправлення

1. Закрити seller bypass у `/me/shop`.
2. Виправити `isAssignment`, щоб підхоплював parked order.
3. Визначити єдину політику зайнятого магазину.
4. Централізувати displaced seller через `unassignSellerAndPark()`.
5. Додати locks у bulk route.
6. Уніфікувати socket/cache post-commit.
7. Заборонити raw update через `POST /users`.
8. Видалити `DeliveryGroup.members` зі схеми та живої БД.
9. Після стабілізації розглянути видалення `User.deliveryGroupId` як збереженого поля.

# Мінімальна матриця E2E перед релізом змін

- продавець без замовлення: магазин A → B;
- продавець з активним замовленням до picking: A → B;
- продавець із хоча б однією completed picking task: перенесення блокується;
- зняття з магазину з активним замовленням → parked;
- parked seller → первинне призначення в B;
- B вільний / B має одного продавця / B уже в конфлікті;
- B у поточному picking → замовлення йде в next session;
- перенесення через admin user form, shop form, request approval та invite;
- два одночасні перенесення одного продавця;
- відкритий Mini App продавця отримує новий профіль без reload;
- старі завершені замовлення не змінюють історичний магазин;
- дозамовлення лишається прив'язаним до магазину, де його створено.
