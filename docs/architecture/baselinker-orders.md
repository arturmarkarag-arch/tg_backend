# BaseLinker multi-account fulfilment contract

Status: **greenfield contract**. This module has no production data to preserve and deliberately contains **no BaseLinker legacy migrations, fallback credentials, fallback identities, or backward-compatible single-account routes**.

## 1. Boundary and authorities

BaseLinker is the external source of truth for BaseLinker order data, upstream order status, connected order sources, catalog/inventory metadata, courier packages and labels.

Our MongoDB is authoritative only for data that belongs to our application:

- the durable identity/configuration of each BaseLinker connection;
- local fulfilment/picking state and ownership;
- local problem resolution state;
- local packing/sent audit;
- minimal queue membership/index data required for scalable server-side paging/filtering;
- print jobs and audit/history that our application itself creates.

BaseLinker orders are not inserted into the seller/group/session `Order`, `OrderingSession`, `PickingTask` or delivery-group workflow. Those are separate domains with separate invariants.

The only intentional BaseLinker order-status write in this module is the operator action **Відправив**. It calls `setOrderStatus` for the configured Sent status of the same BaseLinker account and then exact-rereads that order before local Sent is persisted. There is no CRM cancellation write path and no generic order-field mutation path.

Official API references:

- https://api.baselinker.com/
- https://api.baselinker.com/index.php?method=getOrders
- https://api.baselinker.com/index.php?method=getOrderStatusList
- https://api.baselinker.com/index.php?method=getOrderSources
- https://api.baselinker.com/index.php?method=getInventories
- https://api.baselinker.com/index.php?method=getJournalList

## 2. Root identity: `BaseLinkerAccount`

BaseLinker public API does not provide a durable global account ID suitable as our database identity. Every BaseLinker connection therefore receives **our own UUID** at creation time:

```text
BaseLinkerAccount.accountId = UUID generated by our server
```

This UUID is immutable for the lifetime of that connection in our system.

A BaseLinker account record contains, at minimum:

```text
BaseLinkerAccount
  accountId            OUR UUID, required, unique
  name                 display name only
  color                optional UI decoration
  enabled              runtime on/off switch
  tokenEncrypted       encrypted server-only API token
  tokenFingerprint     secret-derived duplicate guard, never public
  tokenHint            last 4 chars only, UI-safe
  queue                 required Intake/Sent/Cancelled mapping
  metadataSnapshot     API-derived statuses/sources/inventories snapshot
  metadataFetchedAt
  lastSuccessfulSyncAt
  lastSyncError
  lastConnectionCheckAt
  lastConnectionError
```

Names are never identities. Tokens are credentials, never business/database IDs. Metadata contents are never used to infer account identity.

### New account versus token rotation

These are two different administrative operations:

1. **Add BaseLinker account** — creates a new UUID and a new namespace.
2. **Replace API token for this account** — keeps the existing UUID and requires an explicit administrator confirmation that the new token belongs to the same real BaseLinker account.

The system must never guess that a new token represents the same real account based on matching shop names, source IDs, inventory IDs, status names or order numbers.

## 3. Canonical composite identities

Every BaseLinker-owned identifier is scoped by our account UUID.

### Order

```text
(accountId, order_id)
```

`order_id` alone is never a local/global identifier.

### Order source / shop / marketplace account

```text
(accountId, order_source, order_source_id)
```

`order_source_id` is not sufficient by itself. The display name returned by `getOrderSources` is a label only.

### Product/catalog identity

```text
(accountId, storage, storage_id, product_id)
```

When variant identity matters, `variant_id` is additionally part of the product-line identity.

### Package / shipment

```text
(accountId, package_id)
```

Package ownership is additionally verified against the exact order before label retrieval/printing.

### Status

```text
(accountId, status_id)
```

Status IDs from two different BaseLinker accounts are unrelated even when the numeric values match.

### Journal entry

If journal acceleration is enabled in future/current runtime:

```text
(accountId, log_id)
```

A journal ID is never cross-account identity.

### Frontend/runtime order key

```text
accountId + ':' + orderId
```

The same composite identity is required for:

- React/TanStack Query caches;
- optimistic picking intents;
- mutation queues;
- row busy/error state;
- socket events;
- locks;
- active picking recovery;
- package cache invalidation.

A precomputed `orderKey` received through a socket is not trusted as identity. The client derives it from the canonical `(accountId, orderId)` pair and validates the incoming state carries the same pair.

## 4. Token security

There is no `BASELINKER_API_TOKEN` runtime fallback.

All BaseLinker API tokens are stored only in `BaseLinkerAccount` and encrypted at rest with AES-256-GCM using the server secret:

```text
BASELINKER_TOKEN_ENCRYPTION_KEY
```

The AES-GCM associated authenticated data (AAD) is the immutable `accountId`. Therefore encrypted token material copied to a different account document cannot be successfully decrypted for that other account.

The raw token:

- is accepted only on explicit admin create/validate/rotate requests;
- is never returned by the API;
- must not be logged;
- is represented to the UI only by `tokenHint`;
- has an HMAC fingerprint used only to reject connecting the same exact credential to multiple account records.

`BASELINKER_TOKEN_ENCRYPTION_KEY` is a persistent deployment secret. Replacing it without a deliberate token re-encryption procedure makes existing encrypted tokens unreadable. There is intentionally no silent key fallback.

## 5. Atomic account creation

A BaseLinker account cannot exist in a half-configured state.

Before creation the server performs read-only token validation against BaseLinker:

```text
getOrderStatusList
getOrderSources
getInventories
```

The administrator then selects three **distinct** statuses from the returned status list:

- Intake / ready for our warehouse flow;
- Sent;
- Cancelled.

The account document is created once, already containing:

- UUID;
- encrypted token;
- validated queue mapping;
- API metadata snapshot.

If token validation or queue validation fails, no account row is created.

## 6. Queue status contract

Each account has its own required queue configuration. **Only the three status IDs are persisted in the queue configuration.** Human-readable status names are always resolved from that account's latest API-derived `metadataSnapshot.statuses`; names are never identity and are never a second configuration source.

All three status IDs must be positive, distinct and present in that account's current BaseLinker status metadata at save/create time.

There is no global BaseLinker queue setting and no old `statusId` fallback.

The Intake status is the only status scanned as an upstream queue. Local workflow is then controlled by our picking state and exact upstream reconciliation; a locally tracked order does not lose our operational history merely because it moves away from Intake.

Sent and Cancelled are **not** periodically mirrored as BaseLinker status lists. They are terminal classifications learned from exact rereads of locally admitted orders, while their bounded history shelves live in `BaseLinkerPickingOrder`.

## 7. Source metadata and snapshots

`getOrders` provides technical source identity (`order_source`, `order_source_id`). `getOrderSources` provides human-readable names.

For a tracked order, store both:

```text
baseLinkerAccountId
sourceType                order_source
sourceId                  order_source_id
sourceNameSnapshot        historical human-readable label
sourceNameLastKnown       refreshable human-readable label, where used
```

Technical truth is `(accountId, sourceType, sourceId)`. A source name snapshot exists so historical orders remain understandable after a connected store/account is renamed or removed.

`BaseLinkerOrderIndex` stores `sourceType` and `sourceId` as minimal non-personal technical fields. This is necessary for truthful **server-side** source filtering and pagination. Filtering only after a numbered page has been fetched would produce incorrect counts and page boundaries.

## 8. Minimal queue index

The queue index is not an order mirror.

It may persist only minimal operational/index fields such as:

- `baseLinkerAccountId`;
- `orderId` / numeric cursor helper;
- queue/shelf membership;
- upstream disposition/status metadata needed by reconciliation;
- source type/source ID for server-side filtering;
- stable sort timestamp (`date_confirmed`/`date_add` projection as required);
- sync token/seen timestamps.

It must not persist the whole BaseLinker order, customer profile, address, phone, email, product payload or arbitrary raw API response.

Tracked `BaseLinkerPickingOrder` documents may persist the minimal order/product snapshot needed to continue our own picking/audit workflow after admission.


## 9. Intake-only upstream scan and exact departure reconciliation

The regular queue scanner calls `getOrders` only for the configured Intake status:

```text
status_id = account.queue.intakeStatusId
id_from   = forward BaseLinker cursor
```

There is deliberately **no date/period scan mode** (`date_confirmed_from`, `date_from`, etc.) and no periodic full scan of Sent or Cancelled statuses.

`getOrders` pages are followed with `id_from`; BaseLinker returns at most 100 orders per call. Scan depth is bounded from the configured per-token request budget and refresh cadence. If the safe bound is reached while another page still exists, the scan is marked truncated and the current index is not silently accepted as complete.

When an order that was previously in Intake is absent from a fresh Intake scan, absence is not treated as proof of its new state. Departures are verified in bounded batches with an exact account-scoped `getOrders(order_id=...)` reread.

For each exact reread:

- Intake again -> keep/restore production eligibility;
- configured Sent -> materialize the terminal local `Sent` outcome; this status means the order is already packed/shipped;
- configured Cancelled -> move the order to the Cancelled outcome; if warehouse work had already happened, keep that history and raise an Updated/problem flag;
- another status -> record the exact upstream disposition and block production;
- missing/unavailable/failed verification -> do not guess; block production fail-closed.

The configured statuses are the production contract: Intake is the only actionable status, Sent is a terminal shipped outcome, and Cancelled is a terminal cancellation outcome. Local packing/picking progress remains a separate audit trail and is never erased by later status changes.

Only **verified** departures are removed from the current Intake index. If more departures exist than the per-sync verification allowance, the remainder stays indexed and is retried on later synchronization. This is deliberate fail-closed eventual consistency.

Tracked orders continue bounded exact reconciliation even after they leave Intake. This is required to observe transitions such as `Other -> Cancelled`, `Other -> Sent`, or `Sent -> Cancelled` after the Intake index row has already been removed. Selected UI reads also run a small TTL-protected re-verification batch so visible local cards do not remain stale between scheduler ticks.

Selected UI pages may hydrate only the current 10/20 visible order identities. Concrete fallback reads are exact `(accountId, orderId)` requests and remain within the same per-token request budget.

## 10. Global sorting across accounts

`order_id` sequences are independent per BaseLinker account. Therefore a combined queue must never interpret a larger `order_id` as a newer cross-account order.

Global sorting uses a BaseLinker timestamp (`date_confirmed` / `date_add` according to the queue projection contract). Account/order identity is used only as a deterministic tie-breaker.

## 11. API-only integration

All operational BaseLinker reads/writes go through the official BaseLinker API with the token belonging to the selected account.

The server exposes account-scoped application routes for entity-specific operations. Canonical shape:

```text
GET /accounts/:accountId/orders/:orderId
/accounts/:accountId/orders/:orderId/...
/accounts/:accountId/picking/orders/:orderId/...
```

The paged `/orders` endpoint is list/filter only and rejects an `orderId` query shortcut. There is no route that mutates or exact-reads a specific BaseLinker order using only `orderId`.

Admin account management is separate under `/admin/baselinker-settings/...`.

## 12. Rate isolation and failure isolation

BaseLinker documents a per-token API request limit. The client keeps a separate request budget per account/token and deliberately operates below the published limit.

Each enabled account has independent:

- synchronization state;
- backoff/error state;
- metadata state;
- API request budget.

Failure/authentication/rate limiting of Account A must not stop Account B..N.

Parallel account work may be bounded globally to protect our own process, but correctness and error state remain account-scoped.

## 13. `getJournalList` is optional acceleration, not authority

The architecture must remain correct without journal.

Journal may be unavailable/disabled and its visible history is bounded. Therefore it can be used only as an incremental change detector/accelerator:

```text
journal event
  -> identify account + affected order
  -> exact getOrders(order_id)
  -> reconcile canonical state
```

Periodic/status-based reconciliation and exact reads remain the correctness path. No local business state is considered authoritative merely because a journal event was or was not observed.

## 14. Account lifecycle: disable, token rotation and queue-status edits

`enabled=false` means **zero ordinary BaseLinker runtime traffic for that account**, but disabling is not a casual pause button.

The server must refuse disable while the account has any unfinished production lifecycle work, including:

- any current Intake queue row;
- any local picking order that is not resolved local Sent or reviewed upstream Cancelled;
- any unresolved upstream review/problem;
- any active owner/claim;
- any pending/claimed/printing print job.

Before disable, the server forces a fresh Intake synchronization **and** bounded exact reconciliation of tracked orders under the same account lifecycle lock used by new claims. If BaseLinker cannot be verified, or the bounded pass still has unverified departures/tracked rows, disable fails closed and must be retried after reconciliation. This prevents stale-queue disable, stale post-Intake status decisions, and the race:

```text
disable checks empty
-> worker claims
-> account becomes disabled
```

Changing the configured Intake/Sent/Cancelled status IDs uses the same lifecycle boundary, requires complete fresh reconciliation, and is forbidden while unfinished production work exists. Display name and color remain editable.

API token rotation is intentionally different. A broken/deleted BaseLinker token must be replaceable even while unfinished orders exist. Rotation preserves our immutable `accountId`, local orders, progress and history.

Disabled accounts:

- are excluded from background synchronization;
- are excluded from normal metadata refresh;
- cannot execute ordinary production BaseLinker operations;
- keep local history and snapshots;
- are not purged merely because upstream cannot be queried.

Explicit administrator maintenance is the only exception. An admin may deliberately validate/refresh/rotate credentials while disabled.

Hard delete is intentionally not implemented. Disabling never deletes the account UUID or historical identity.

## 15. Picking identity and ownership

Every BaseLinker picking document and every order lock is account-scoped:

```text
(baseLinkerAccountId, orderId)
lock = baselinker-order:<accountId>:<orderId>
```

MongoDB unique indexes use the same composite identity.

The business rule **one worker may own at most one active BaseLinker order globally** remains intentionally global across all BaseLinker accounts. This is a worker-capacity rule, not an order-identity rule.

Optimistic concurrency/version checks remain a durable backstop against concurrent updates.

## 16. Current item/workflow states

Current writable line states are only:

```text
pending
picked
shortage
not_found
```

There are no legacy `damaged`/`other` line-state fallbacks.

Current explicit workflow stages are required. Missing stages are invalid data; they are not reconstructed from old status fields.

Packing writes only the current full-packing contract. There is no legacy `partial` / `with_issue` packing-mode compatibility path.

A line problem (`shortage` / `not_found`) is explicit local work. All lines may be handled while unresolved issues still exist; however final packing is blocked until unresolved problems are resolved under the current picking contract.

## 17. Production eligibility and immutable warehouse facts

The configured Intake status is the **only** upstream state in which warehouse production may advance.

```text
actual BaseLinker order_status_id == account.queue.intakeStatusId
  -> production eligible

anything else: Sent / Cancelled / other / missing / unverified
  -> production blocked
```

Critical production transitions (`claim`, `Packed`, `Sent`) use exact account-scoped BaseLinker verification. Item edits may use the short verification TTL plus background reconciliation, but the final physical transitions never trust a stale page.

When an exact/background observation leaves Intake:

- current ownership is released so a worker cannot deadlock;
- picked quantities, item problems and history are preserved;
- pre-fulfilment workflow becomes blocked/deferred;
- the card reports the actual upstream status and allowed Intake status;
- `Release/Відкласти` remains a local operation and never depends on BaseLinker availability/status.

Two truths are stored separately:

1. **Local fulfilment/audit truth** — picking/packing progress and the terminal Sent outcome observed by our system.
2. **Current BaseLinker truth** — the latest exact upstream status/order data.

The configured BaseLinker `Sent` status materializes the terminal local `Sent` outcome because, for this workflow, `Wysłane` means the order is already packed and shipped. If the warehouse itself performs the Send action, that action writes the same terminal outcome and moves BaseLinker to the configured Sent status when necessary.

Once `Packed` or `Sent` has been recorded, that fulfilment snapshot is immutable. Later BaseLinker product/status changes do not erase the packed item snapshot or the recorded Sent fact. They may create an upstream review/problem instead.

Examples:

```text
Warehouse Sent + BaseLinker Cancelled
  -> physical Sent remains
  -> current upstream = Cancelled
  -> visible in Cancelled
  -> also visible in Updated while review is required

Warehouse Packed + BaseLinker other status
  -> physical Packed remains
  -> production cannot advance until upstream is resolved/returns to Intake
  -> Updated while review is required

Not yet Packed/Sent + BaseLinker Cancelled
  -> blocked Cancelled + Updated
  -> after explicit review acknowledgement, cancellation is lifecycle-terminal
```

`Updated` is therefore an orthogonal attention flag (`upstreamReviewRequired`), not a replacement for the main shelf. A card may be both Cancelled and Updated.

Acknowledging a review never fabricates a physical warehouse action and never makes a non-Intake order production-eligible.

Admin reopen cannot erase a recorded physical Packed/Sent fact.

## 18. Packages, labels and printing

Every package/label operation carries both account and order identity and uses the caller bound to that account token.

Before label retrieval or print queueing, the server verifies that the requested `package_id` belongs to the exact `(accountId, orderId)` order returned by BaseLinker.

Print jobs persist `baseLinkerAccountId`; package deduplication is never global by package ID alone.

Frontend package query keys are account/order scoped so socket invalidation for Account A cannot stale or replace Account B with the same numeric order/package IDs.

## 19. Retention is fail-closed

Local bounded BaseLinker history may be cleaned only when the retention contract positively proves the row is eligible.

A failed API call, disabled account, authentication failure, timeout or unknown upstream state is **not proof that a row may be deleted**.

`upstreamReviewRequired=true` is an absolute retention blocker. An unresolved post-pack/post-send conflict must never disappear merely because 14 days elapsed.

The configured BaseLinker `Sent` status materializes the canonical local `Sent` outcome, so it is retention-terminal once its 14-day age is satisfied and no unresolved review exists. Reviewed upstream cancellations are also terminal candidates. Every candidate is exact-verified fail-closed before deletion, and a newer upstream change restarts the 14-day age.

Disabled accounts therefore retain local history until explicitly re-enabled/verified or separately administered.

## 20. Socket contract

Every BaseLinker order/picking realtime event that refers to a concrete order must carry:

```text
baseLinkerAccountId
orderId
```

The client derives its own composite key and rejects a state whose embedded account/order pair does not match the event envelope.

Events and cache invalidation must never key only by `orderId`, `packageId`, source name or any other BaseLinker-local identifier.

## 21. UI contract

The combined warehouse queue may display all enabled BaseLinker accounts together, but every order must visibly retain provenance:

```text
Зам-ня №7834521    [BL Allegro PL]
Allegro Firma PL · зовнішній №...
```

Required filters:

- BaseLinker account;
- source type (`shop`, `allegro`, `amazon`, ...);
- concrete source/store/account.

Account management UI provides:

- Add account;
- token validation;
- per-account status selection;
- enable/disable;
- metadata refresh;
- edit display name/color;
- explicit same-account token rotation;
- sync/connection health and last successful sync.

Tokens are never displayed after submission.

## 22. Greenfield schema policy

There is deliberately **no BaseLinker data migration layer** and **no legacy support**.

The following are invalid design patterns for this module:

- backfilling missing `accountId`;
- accepting old single-account records;
- falling back to an environment API token;
- inferring an account because only one account exists;
- old account-less HTTP routes;
- legacy status/packing/item-state translation;
- automatically dropping/converting old BaseLinker collections at startup;
- guessing the owner account of an orphan row.

The database is expected to start with the current BaseLinker schema. Documents that do not satisfy current required fields are invalid and must not be silently repaired.

Schema/index initialization for the **current** collections is allowed and required; that is not a migration.

## 23. Release collision gate

Before release, tests must explicitly cover at least these collisions:

```text
Account A order_id=123  != Account B order_id=123
Account A package_id=55 != Account B package_id=55
Account A product_id=77 != Account B product_id=77
Account A status_id=9   != Account B status_id=9
Account A allegro/150   != Account B allegro/150
Account A allegro/150   != Account A amazon/150
```

And they must prove isolation in:

- Mongo unique indexes;
- order locks;
- API caller/token selection;
- query keys;
- optimistic mutations;
- busy/error predicates;
- sockets;
- package/print lookups;
- source filters and pagination.

This composite-identity rule is the non-negotiable invariant of the BaseLinker integration.
