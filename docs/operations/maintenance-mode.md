# Maintenance / read-only через критичні індекси MongoDB

## Що відбувається

Якщо сервер не може синхронізувати індекс, який забезпечує бізнесову цілісність, він продовжує відповідати на читання, але блокує всі `POST`, `PUT`, `PATCH` і `DELETE` з кодом `503 maintenance_read_only`.

Стан доступний у:

```text
GET /api/health
GET /api/maintenance
```

У відповіді вказано, яка група індексів зламалась, технічний текст помилки MongoDB і короткі кроки виправлення. Та сама помилка записується в лог сервера з префіксом `[indexes]`.

## Загальна процедура

1. Не обходити maintenance і не вимикати перевірку індексів.
2. Зробити резервну копію бази.
3. Знайти в логах перший запис `[indexes] ... failed`.
4. Перевірити поточні індекси відповідної колекції через `db.<collection>.getIndexes()`.
5. Якщо MongoDB повідомляє `E11000`, знайти дублікати, вирішити який документ правильний, інші об’єднати або перевести в термінальний статус.
6. Якщо заважає застарілий індекс, видалити лише конкретний індекс після перевірки його назви через `getIndexes()`.
7. Перезапустити сервер. `syncIndexes()` створить актуальні індекси й maintenance автоматично не ввімкнеться.


## ShopProduct

Зламана гарантія: непорожній штрихкод у каталозі магазинів має бути унікальним, а товари без штрихкоду не повинні конфліктувати між собою.

Перевірити:

```javascript
db.shopproducts.getIndexes()
```

Актуальний `barcode_1` повинен мати `partialFilterExpression: {barcode: {$gt: ''}}`. Якщо є дублікати непорожніх штрихкодів — спочатку виправити документи, потім перезапустити сервер.

## Order

Зламана гарантія: максимум одне активне замовлення на покупця, магазин і сесію.

Пошук дублів:

```javascript
db.orders.aggregate([
  {$match: {
    status: {$in: ['new', 'in_progress']},
    shopId: {$type: 'objectId'},
    orderingSessionId: {$gt: ''}
  }},
  {$group: {
    _id: {
      buyerTelegramId: '$buyerTelegramId',
      shopId: '$shopId',
      orderingSessionId: '$orderingSessionId'
    },
    ids: {$push: '$_id'},
    count: {$sum: 1}
  }},
  {$match: {count: {$gt: 1}}}
])
```

Після ручного виправлення повторно запустити сервер.

## PickingTask

Зламана гарантія: максимум одна активна задача на `productId + deliveryGroupId`, або в базі лишився старий глобальний індекс `productId_1`.

Перевірити:

```javascript
db.pickingtasks.getIndexes()
```

Якщо існує застарілий унікальний `productId_1`, видалити саме його:

```javascript
db.pickingtasks.dropIndex('productId_1')
```

Якщо є дублікати активних задач — спочатку визначити правильну задачу й закрити/об’єднати інші.

## SupplementOffer / SupplementRequest

Зламані гарантії:

- одна пропозиція на `receiptItemId + deliveryGroupId`;
- одна заявка магазину на `offerId + shopId`.

Зверніть увагу: індексу `productId + deliveryGroupId` більше не повинно бути. Якщо в базі лишився старий індекс, `syncIndexes()` має його видалити. У разі помилки перевірити:

```javascript
db.supplementoffers.getIndexes()
db.supplementrequests.getIndexes()
```

Не видаляти документи автоматично: спершу звірити накладну, групу та магазин.

## User

Зламана гарантія унікальності Google identity (`googleEmail`, `googleSub`). Знайти дублікати, залишити правильний акаунт, перенести потрібні зв’язки й лише потім перезапустити сервер.

## Побічні записи під час читання

У старій архітектурі частина `GET` і профільних запитів викликала `getOrCreateSessionId()` та могла створити `OrderingSession` як побічний ефект читання.

У режимі maintenance обидва хелпери `getOrCreateSessionId()` і `getOrCreateNextSessionId()` працюють як `find-only`: повертають наявний ID або `null`, але не створюють документ. Тому read-only стосується не лише HTTP-методу, а й прихованих записів під час завантаження сторінок.
