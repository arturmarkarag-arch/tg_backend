# 5 серпня 2026 — індекси, повторні дозамовлення та документація

## Змінено

1. Видалено унікальну заборону `productId + deliveryGroupId` для активних `SupplementOffer`.
2. Різні накладні можуть одночасно відкрити той самий товар одній групі.
3. Усередині однієї накладної однаковий товар як і раніше показується один раз.
4. Критичні помилки синхронізації індексів переводять API у `maintenance_read_only`.
5. У maintenance:
   - читання продовжує працювати;
   - `POST/PUT/PATCH/DELETE` повертають 503;
   - Telegram-бот і фонові планувальники не запускаються;
   - `/api/health` і `/api/maintenance` показують причину та інструкцію.
6. Додано інструкцію відновлення MongoDB-індексів.
7. Актуальну бізнес-логіку винесено в `docs/receipt/readme.md` і `docs/supplement/readme.md`.
8. Відкладені питання `Product/ShopProduct/SearchProduct`, дублювання групи та стара shift-модель записані в технічний борг.
9. Історичні коментарі й посилання на старі параграфи прибрані з коду дозамовлень.
10. Виправлено випадковий дубль поля `history` під час створення `SupplementRequest`.
11. Maintenance-відповідь показує технічний текст помилки MongoDB та покрокове відновлення.
12. У maintenance старі `getOrCreateSessionId()`-виклики працюють без створення документів, тому GET/profile не роблять прихованих записів.

## Перевірити після розгортання

1. Перезапустити сервер і переконатися, що `SupplementOffer.syncIndexes()` видалив старий індекс `productId_1_deliveryGroupId_1`.
2. Провести дві накладні-дозамовлення з тим самим товаром для однієї групи.
3. Переконатися, що у продавця й складу видно дві незалежні пропозиції.
4. Перевірити `/api/health`: у нормі `status=ok`, `maintenance.active=false`.
5. На тестовій БД навмисно створити конфлікт індексу й перевірити 503 `maintenance_read_only` на запис.

## Не змінювалось

- облік `Product.quantity`;
- Telegram-групи безпеки/розсилки;
- стара shift-модель;
- OOS, резервування та часткове виконання дозамовлень.
