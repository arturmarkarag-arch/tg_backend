# Allegro: актуальність даних, версія 2

## Джерела та правила

Allegro є джерелом стану замовлення. MongoDB зберігає локальну проєкцію для списку, пошуку та пагінації; стан збирання належить нашому складу. Оновлення сторінки перечитує проєкцію. Оновлення даних Allegro виконується на сервері незалежно від відкритого браузера.

| Дані | Як оновлюються | Правило за замовчуванням |
| --- | --- | --- |
| Події замовлень | Окремий планувальник для кожного магазину, курсор у MongoDB | Запуск кожні 5 с; для зайнятого магазину наступний запуск пропускається |
| Деталі замовлень | Точний GET після релевантної події | До 200 оновлень сумарно за цикл, 2 одночасні запити |
| Активні замовлення без подій | Контрольне звіряння за найдавнішим `seenAt` | Замовлення старші 60 с, до 10 за цикл; після обробки журналу |
| Фото пропозицій | Окреме фонове завдання, ключ `accountId + offerId` | Позитивний результат — 6 год; підтверджена відсутність — 30 хв |
| Помилка фото | Зберігається останнє відоме фото та помилка | Повтор не раніше 60 с; враховується більший Retry-After |
| Відправлення | Одна команда створення, далі GET статусу | Час наступного GET зберігається відповідно до Retry-After |
| Критичні складські дії | Точна перевірка Allegro перед дією | SENT додатково використовує `checkoutForm.revision` |

Часові інтервали є цілями, а не гарантією затримки. При великій черзі, недоступності провайдера чи вичерпанні лімітів перевірка триває довше. Наприклад, повний контрольний обхід 1000 замовлень пакетами по 10 за ідеального циклу 5 с потребує щонайменше близько 8 хвилин. Оперативні події мають пріоритет над контрольним обходом.

## Зміни в архітектурі

- Прибрано глобальний прапорець зайнятості планувальника: зависання одного магазину не затримує наступний цикл іншого.
- Фото виконуються окремо від блокування синхронізації замовлень. До 12 пропозицій за завдання, 2 паралельні запити; декілька замовлень використовують спільний результат для тієї самої пропозиції магазину.
- Оновлюються і наявні фото. Негативні результати та помилки мають термін повторної перевірки; HTTP-помилка не оновлює час успішної перевірки.
- Фото змінюють лише поля зображень через arrayFilters за ідентифікатором пропозиції. Фонове завдання не записує стару копію всього списку товарів поверх нового замовлення. `seenAt` захищає встановлення часу наступної перевірки від паралельного оновлення замовлення.
- Частково оброблений журнал має стан `catching_up`. `lastSuccessfulPollAt` означає успішний запит, `lastCaughtUpAt` — обробку всіх доступних подій. Ці поняття розділено.
- Невалідна відповідь журналу не може пересунути курсор. Ліміт детальних GET тепер загальний для всіх сторінок циклу.
- При помилці одного паралельного завдання очікується завершення інших перед звільненням блокування.
- Повторна побудова проєкції перевіряє відсутні в активному списку замовлення точним GET; SENT/CANCELLED більше не втрачають історію через відсутність у фільтрі. Видалення залишається для підтвердженого 404 або переходу до іншого провайдера виконання.
- Підготовка відправлення звіряє товари зі складським станом; зміни потребують повторного перегляду. Наявна етикетка доступна без повторного створення відправлення.
- Інтерфейс показує непідтверджену синхронізацію, помилку оновлення списку та час перевірки конкретного замовлення. Після помилки складської дії локальні запити оновлюються.

## Перевірка та розгортання

`npm run test:allegro:freshness` виконує поведінкові перевірки з ізольованими залежностями: прострочення позитивного/негативного кешу, помилки, ізоляція магазинів, некоректні відповіді, ліміт циклу, завершення паралельних робіт, повторна побудова, повільний магазин, строки опитування відправлення та зміна товарів перед створенням ТТН.

Нова колекція `AllegroOfferImage` та індекси підключені до штатного запуску сервера. Старі замовлення без `nextImageCheckAt` потрапляють у фонову перевірку автоматично. Дані не потребують очищення чи ручного скидання кешу. `synchronizationVersion: 2` у `/allegro/status` позначає нову поведінку; версія складського API залишається сумісною.

Для бойової перевірки потрібні перезапуск/розгортання сервера та клієнта, підключений магазин і контрольний наскрізний сценарій. У цій зміні живі замовлення, відправлення й токени не змінювались.

## Межі та наступні перевірки

- Потрібно виміряти фактичний час контрольного обходу на кількості замовлень кожного магазину й налаштувати бюджет за результатом. Перевіряються активні полиці; історичні відправлені замовлення оновлюються за подіями.
- Для старої команди відправлення зі статусом pending та GET 404 автоматичне повторне створення залишається заблокованим: спочатку слід з'ясувати результат попереднього POST. Повноцінне автоматичне відновлення цього сценарію потребує стійкого збереження точного запиту створення та його ревізії. Підтверджена помилка команди також повертається користувачу без прихованого повторного POST.
- Розподілені блокування мають обмежений TTL. Під час навантажувальної перевірки потрібно перевірити тривалість початкового імпорту й тривалих запитів; відновлення після втрати Redis lease залишається окремим завданням.
