**Продавці, магазини та старий стан кошика — виправлення від 05.09.2026**

Виправлення зроблено поверх наданих client(20260905-single-problem-badge)(1).zip та server(20260905-workflow-stage-cache-fix)(1).zip. Доданий висновок іншого чату звірено з цим кодом. Робочу або тестову віддалену MongoDB не підключав, документів у ній не змінював. Попередні цифри про 201 користувача та розміри BSON повторно не вимірював.

Причина запиту на 500 продавців справді була в неправильному джерелі даних форми: вона шукала призначених у глобальному масиві користувачів. Зараз джерело призначення — User.shopId, а форма отримує призначених продавців у sellers конкретного магазину. Розмір списку кандидатів більше не визначає, чи буде видно вже призначену людину.

Новий пошук працює за ім’ям і прізвищем, телефоном, Telegram ID, @username, назвою/адресою магазину та містом. Слова поєднуються через AND, поля — через OR. Продавці з accountState=removed не потрапляють до кандидатів, а старі документи без accountState продовжують вважатися активними. Пошук не змінює призначень: кнопки викликають наявні канонічні команди перенесення/зняття.

Для порожнього пошуку форма запитує лише вільних продавців. Перехід на наступну сторінку робить окремий запит; автоматичного обходу всіх сторінок немає. Запити мають ключі за магазином, пошуком, режимом і сторінкою та отримують AbortSignal. Помилка кандидатів не приховує призначених продавців; є повідомлення й повторне завантаження. При створенні нового магазину список кандидатів не запитується.

| GET /api/shops?page=1&pageSize=20 | Сторінка магазинів і призначені саме до них seller/admin. Збережено потрібні чинним екранам поля currentAssignment, sellerNames та службові ознаки магазину. |
| GET /api/users/assignment-candidates?shopId=ID&scope=unassigned&page=1&pageSize=20 | Сторінка вільних активних продавців. |

У звичайному /shops більше немає агрегації останнього замовлення кожного продавця. Окремий пошук ознак активних замовлень за явно переданою orderingSessionId збережено: він потрібен екрану вирішення конфліктів. Історія колишніх продавців також не стерта: сервер вибирає лише релевантні події для магазинів відповіді та повертає короткий результат. Форма не називає колишнього продавця «вільним», якщо не має підтвердження його поточного призначення.

Додатково звужено вибірку користувача в middleware авторизації: кожен звичайний запит більше не читає його історію та кошик заради перевірки ролі. Перевірки блокування, видалення облікового запису та відкликання JWT збережено.

Із cartState не можна було видаляти все. Зараз його контракт для навігації такий:

```json
{
  "navigationSessionId": "ідентифікатор сесії",
  "lastViewedProductId": "ідентифікатор товару",
  "currentIndex": 1278,
  "updatedAt": "2026-09-05T01:00:00.000Z"
}
```

navigationSessionId захищає від старої сесії, lastViewedProductId відновлює позицію за стабільним ключем, currentIndex лишається запасною позицією. Номер сторінки клієнт рахує зі свого розміру сторінки: для індексу 1278 і розміру 10 це 127. Зберігати його другим незалежним числом у Mongo більше не потрібно. Старий клієнт може передати currentPage, але сервер не записує його.

Припинено запис orderItems, orderItemIds, lastOrderPositions, lastViewedOrderNumber та currentPage у User.cartState. Кількості залишаються в Order. При цьому записи User з перевіркою очікуваного shopId всередині транзакцій Order збережено: це захист від конкурентного перенесення продавця, а не просто зайве оновлення кошика. miniAppState повертає лише updatedAt. Невикористані activeSellerCount та lastModifiedBy-поля більше не додаються до профілю; зайвий count активних продавців при відкритті профілю прибрано. Reset-state скидає приватну навігацію одним записом, включно з користувачами без магазину, і не будить дошки пакування.

Старе «відновлення кошика» було функціонально хибним: успішна відповідь не створювала й не оновлювала Order. У ClearedCart немає orderingSessionId та канонічного Order, тож автоматичний перенос цього знімка в поточну сесію означав би припущення про власника й сесію. У цьому випуску кнопка прибрана, а запит від старого клієнта повертає 409 cleared_cart_legacy_unrestorable. Знімки й старі позначки відновлення збережено як історичні дані. Наявний механізм /orders/:id/stale/restore-to-cart для справжніх Order залишається; він має власну перевірку сесії, маршруту і приналежності. Нової автоматичної конвертації ClearedCart у Order немає.

Фізичне очищення Mongo відокремлено від розгортання коду. Вже після оновлення серверних процесів можна виконати read-only інвентаризацію з каталогу server:

```bash
node scripts/cleanupUserDirectoryLegacyFields.js
node scripts/inspectUserDirectoryReadPlans.js
```

Перший скрипт лише рахує документи зі старими полями. Другий читає індекси та explain(executionStats) для призначених продавців, вільних кандидатів і сторінок користувачів. Жоден із цих двох викликів не змінює базу й не запускається автоматично під час старту застосунку.

Для окремої операції фізичного очищення підготовлено режим:

```bash
node scripts/cleanupUserDirectoryLegacyFields.js --apply --backup /absolute/path/user-directory-legacy-backup.jsonl
```

Перед першим $unset він повністю записує новий файл резервної копії з точними BSON-значеннями старих полів; існуючий файл не перезаписує. Кожен документ оновлюється лише якщо збережені поля досі збігаються з копією. Змінені паралельно документи пропускаються. Сесії, живі координати навігації, User.history, Google-ідентичність та Order цей скрипт не очищає. Я режим --apply не виконував.

Для старих top-level полів ReceiptItem у проєкті вже є cleanupReceiptContractLegacyFields.js; він збережений. Embedded telegramNewProduct та photoMeta.comment/commentPos не видаляв: у наданій версії їх ще читають механізми сумісності/міграції. SupplementOffer і SupplementWave не є мертвими моделями лише через нуль документів у попередньому замірі. Підстав видаляти ці живі контракти немає.

Індекси User: shopId + role + createdAt + _id; role + createdAt + _id; createdAt + _id. Усі неунікальні, без partial-умови accountState, тому не виключають legacy-користувачів без цього поля. Їх фактичне створення залежить від штатних налаштувань індексації Mongoose при розгортанні. Замірів прискорення на вашій Mongo немає; unanchored текстовий пошук також не слід вважати повністю індексованим. Гарантована зміна цього випуску — обсяг даних та межі запитів, а не заявлений відсоток прискорення.
