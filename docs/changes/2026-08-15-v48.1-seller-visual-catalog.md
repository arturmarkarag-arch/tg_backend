# V48.1 — logical visual ordering for seller catalogue

## Final scope
Presentation only for `Товари → Товари`.

The visual-order code does **not** mutate:
- `Block.productIds`;
- `Product.orderNumber`;
- `PickingTask` / `positionIndex`;
- `OrderingSession`;
- orders or supplement flows.

## Eligibility remains business-authoritative
`GET /api/v1/products/catalog` starts from products that are:
- `Product.status === active`;
- `orderingEnabled !== false`;
- physically present in a `Block.productIds`;
- not newer than the current seller cycle cutoff.

Therefore goods still in `Надходження`, supplement-only technical Products, and mandatory-only goods never enter the ordinary seller carousel.

## Visual sequence
The backend loads existing `ProductVector` image embeddings for that already-eligible set.

1. Compatible embedding dimensions/model family are selected.
2. For small sets, exact cosine vectors are used.
3. For large sets, a deterministic cosine-preserving feature-hash sketch is used to keep first-build latency bounded.
4. A deterministic edge start is selected.
5. Greedy nearest-neighbour sequence is built.
6. Up to four 2-opt passes reduce bad transitions.
7. Products without a compatible embedding are appended at the stable fallback tail.

No categories, cluster names or AI product types are created.

## Stability
The resulting ID sequence is cached per delivery-group ordering cycle. During the same cycle:
- archive/removal only closes a gap;
- an update does not reshuffle the seller under their current index;
- an unexpected legacy eligible item is appended, not used to rebuild the whole order.

Next cycle gets a fresh visual sequence and therefore can use new embeddings/products.

## Mongo/Atlas
No new MongoDB collection or Atlas Vector Search index is required. V48.1 reads the existing `ProductVector.geminiVector` rows directly for one cycle build; Vector Search itself is not used for the global sequence.
